## Reported regression and provenance

Douglas reported missing map marks and more 3D-to-native/previous-view behavior in the preview. The following inspection read EXE/manifest/source/config/logs only; it did not open, parse, restore or copy a human save, change a setting or touch the active game.

- **Correct payload on disk:** all 228 preview payload files match the pinned manifest; EXE remains `337eba…`, manifest `5f68e…`, and `Start-Version.ps1` matches launcher SHA `930b56e50d7848c330bd01cb2e0ca6af8e34310b56be8dd36bbb89c4b52cd491`. The CMD pins that manifest; PS1 resolves its EXE and supplies the separate profile through explicit config/save arguments. No overwritten preview file was found.
- **Current process is not proof of the previous test:** a later read-only process snapshot observed the separate b775 checkpoint executable, with no explicit profile arguments in its command line. This identifies that current execution only. Its actual resolved profile and the earlier failing session are not established by inspecting another version's INI. Do not conclude “wrong EXE caused it” or switch/stop the human session.
- **No automap source rollback in R3:** `automap.cpp` SHA `dce2647085dcf426aacebd4cb77c0a82bda37830526b784b46386f6f3c6f8bb9`, `automap.h` SHA `d975a2014e6828d6a241466fac1d6a3c9f078d37792768659f3118486f2bd3bd`, and `engine/render/automap_render.cpp` match frozen b775, R3 and R4. Minimap header/close/geometry, native tile/player drawing, exploration and conditional nearby-item markers are still present. That does not prove their final composed pixels or the user's exploration match.
- **Own systems retained:** R3 also keeps byte-identical `diablo.cpp`, `track.cpp`, `controls/plrctrls.cpp`, player/actor-position/animation clocks, `town_camera.cpp`, `town_first_person_input.cpp`, main HUD/floating-panel sources, `town_scene.cpp`, `loadsave.cpp` and `pfile.cpp`. The current working tree contains some separate options/pfile WIP; it is not implicitly delivered by a frozen preview.
- **Profile differences are concrete:** preview/habitual respectively use Speed 20/32, FOV 60/80, Zoom 0/1, smoothing 0/1 and brightness 67/15 at inspection. Item labels and health/mana values are off/on. Both have GPU/start-3D enabled, camera mode 3 and saved ToggleAutomap TAB. “Show Item Labels” concerns world labels, not proof of lost map exploration or every class of map mark. Brightness 67 is the observed current value, not attribution of who changed it or when.
- **Independent play state is a hypothesis to test:** native exploration is stored in `AutomapView` and saved/restored by native serializers; the preview uses its own new profile. No human saves were inspected, so differences in explored area/level/item state remain unproven. Do not “fix” this by overwriting the human save or copying it without a defined test scope.
- **Fallback evidence is incomplete:** exact preview log is 6,323 bytes/28 lines, SHA `12c0a9f30f958ae23b4f95b3a6bbab16ef9cd723f61064ccfcb09d192001be6a`. Present samples show RX 570 hardware, modes 2/3, failureKind 0. No Cathedral/first-refusal/entry episode is recorded. It cannot disprove the human report, identify a failed predicate, or show every frame stayed on GPU.

### What First Person reference work actually entered R3/R4?

The R3 receipt differs from frozen b775 Source in **six paths**, not a wholesale reference-engine replacement:

R4 then differs from R3 in `diablo.cpp`, `diablo.h`, `track.cpp` and `town_view.cpp`: native E/stationary-attack dispatch/repeat guards and provisional FP ceiling. Those later changes are **absent from the delivered R3**. Common masonry/independent ceiling, complete reference architectural treatment and HD are still not adapted. The clean checkout layers this candidate; it does not reset the own systems above.

## What can be removed now?

No runtime removal has enough cross-build evidence in this pass. In particular, CPU/native recovery, GPU resident buffers, native command/network plumbing, save serializers, UI recovery and prepared asset tools have purposes outside one visible camera scene. No broad cleanup or automatic deletion is justified.

The immediate safe corrections are documentary: consistent build qualification, Home/F4 behavior, active Meshy OFF status, exact Speed-profile discrepancy, and explicit ownership/lifecycle contracts. Small future code removals require an exact obsolete caller/flag finding, a candidate-only patch and appropriate native/web/save/net tests. Keep any legitimate alternative backend.
